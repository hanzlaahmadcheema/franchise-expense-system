# Agent Prompt: Enforce One Universal Calendar, One Universal Control Bar, and Improved Autosave

You must refactor the app so there is **only one Universal Calendar** and **only one Universal Day Control Bar** used across the whole application. The app may have multiple business modules like Expense, Jazz Load, Stock, and future modules, but it must not create separate calendar components, separate close/reopen buttons, or separate day-control bars inside each module.

This is a hard architectural rule.

## Main Goal

Create one shared daily workflow system:

```text
Universal Calendar
→ Universal Day Control Bar
→ Selected Module Daily Entry
→ Input-Based Autosave
→ Module Calculation Service
→ Shared Day Status / Audit / Recalculation Logic
```

The user should feel like they are working in one unified business app, not jumping between separate mini-apps.

## Hard Rule: Only One Calendar

Create only one calendar component:

```text
UniversalCalendar
```

This must be reused everywhere.

Do not create:

```text
ExpenseCalendar
JazzLoadCalendar
StockCalendar
ModuleCalendar
DailyEntryCalendar
PreviousRecordCalendar
```

If any module already has its own calendar, remove or replace it with `UniversalCalendar`.

The Universal Calendar must handle:

```text
Selected date
Selected month
Today highlight
Past day selection
Future day disabled
Open/closed/missing day indicators
Module-aware record loading
No future record creation
```

The calendar should not belong to Expense, Jazz Load, or Stock. It belongs to the whole app.

## Hard Rule: Only One Control Bar

Create only one shared control bar:

```text
UniversalDayControlBar
```

This must contain these buttons:

```text
Close Day
Reopen Selected Day
Reopen All Days
Close All Previous Days Except Today
Master Calculation Refresh
```

Do not create separate versions like:

```text
ExpenseDayControls
JazzLoadDayControls
StockDayControls
ExpenseCloseButton
JazzLoadReopenButton
StockCloseAllButton
```

If these already exist, remove them or convert them to use `UniversalDayControlBar`.

The control bar should be module-aware through props/config, not duplicated.

Example:

```ts
<UniversalDayControlBar
  moduleKey="stock"
  selectedDate={selectedDate}
  userRole={userRole}
  adapter={stockAdapter}
/>
```

## No Manual Save Button

Daily entry screens should not depend on a Save button.

Remove or de-emphasize manual Save buttons from daily data-entry tables.

The app should work like Excel:

```text
User types value
→ input updates
→ debounce starts
→ data validates
→ data auto-saves
→ calculations update
→ save status changes to Saved
```

Allowed statuses:

```text
Typing...
Saving...
Saved
Offline / Pending Sync
Error
Read-only
Closed Day
```

## Improved Autosave Requirement

Create one reusable autosave hook/service:

```text
useAutoSaveEntry
```

Do not implement different autosave logic in every module.

Required behavior:

```text
Debounced save after typing stops
Recommended debounce: 500–1000ms
Validate before saving
Do not save NaN
Do not save broken empty-number values
Do not save future-day records
Do not autosave if day is closed
Do not autosave if user has read-only permission
Do not overwrite active user typing with stale Firestore data
Show visible save state
Support offline/pending sync
```

Suggested API:

```ts
useAutoSaveEntry({
  moduleKey,
  selectedDate,
  recordId,
  rawData,
  enabled,
  validate,
  saveRawData,
  recalculateDerivedData,
  debounceMs: 800
});
```

Autosave must save **raw user-entered values** first. Calculated fields must be generated by module calculation services.

Do not put formulas inside input components.

## Universal Selected Date State

Create one shared selected date source.

Recommended:

```text
SelectedDateContext
```

or an equivalent global state system.

All modules should read the same selected date from this shared state.

Do not let every module manage its own unrelated selected date.

Required flow:

```text
User selects date in UniversalCalendar
→ selectedDate updates globally
→ active module receives selectedDate
→ active module loads its daily record
→ UniversalDayControlBar updates button states
→ autosave writes to selected date
```

## Universal Day Status

Create one shared day-status model.

Example:

```ts
type UniversalDayStatus =
  | "missing"
  | "open"
  | "closed"
  | "locked"
  | "reopened";
```

Suggested record:

```ts
type UniversalDayControlRecord = {
  moduleKey: "expense" | "jazzLoad" | "stock";
  date: string;
  monthId: string;
  status: UniversalDayStatus;
  closedAt?: Timestamp;
  closedBy?: string;
  reopenedAt?: Timestamp;
  reopenedBy?: string;
  lastMasterRefreshAt?: Timestamp;
  lastMasterRefreshBy?: string;
  updatedAt: Timestamp;
};
```

The control system can be shared while records remain module-aware.

## Button Behavior

### Close Day

When clicked:

```text
Show confirmation popup
If confirmed:
  close selected day
  lock inputs
  stop autosave
  update day status
  write audit log
```

Close Day must not auto-reopen.

### Reopen Selected Day

When clicked:

```text
Check role
Check selected date
Check module
If allowed:
  reopen selected day
  enable inputs
  write audit log
```

Admin can only reopen current day if allowed.

Owner can reopen previous days.

### Reopen All Days

Owner-only.

Must show strong confirmation.

```text
This affects multiple days. Continue?
```

It should reopen days for the selected module/month only unless user explicitly selects global scope.

### Close All Previous Days Except Today

Owner-only or allowed admin-only if existing business rule allows.

Behavior:

```text
Close all open past days up to yesterday
Do not close today
Do not create future records
Write audit log
```

### Master Calculation Refresh

Owner-only by default.

Must show blocking popup with progress.

It recalculates derived values only.

It must not change raw/manual values.

## Master Calculation Refresh Rules

Create one shared service:

```text
masterRecalculationService
```

It should use module adapters:

```text
expenseRecalculationAdapter
jazzLoadRecalculationAdapter
stockRecalculationAdapter
```

The shared service controls the process.
Each module adapter controls its own formulas.

Main rule:

```text
Every day’s closing balance must match the next day’s opening balance.
Every month’s ending closing balance must match the next month’s opening balance.
```

Refresh must recalculate:

```text
Daily calculated fields
Daily summaries
Monthly summaries
Opening balances
Closing balances
Carry-forward chains
Report totals
Consistency checks
```

Refresh must not change:

```text
User-entered quantities
User-entered payments
User-entered expenses
User-entered base amounts
User-entered notes
User-entered assignments
Raw/manual data
```

Progress popup text:

```text
Preparing recalculation...
Loading records...
Recalculating daily balances...
Matching closing to next opening...
Updating monthly summaries...
Checking month-to-month carry-forward...
Refreshing report totals...
Completed.
```

## Adapter Contract

Each module adapter should expose:

```ts
type ModuleDayAdapter = {
  moduleKey: "expense" | "jazzLoad" | "stock";

  loadDay: (date: string) => Promise<any>;
  saveRawData: (date: string, rawData: unknown) => Promise<void>;
  validateRawData: (rawData: unknown) => ValidationResult;

  recalculateDay: (params: {
    date: string;
    openingBalance?: number;
  }) => Promise<RecalculatedDayResult>;

  saveCalculatedOnly: (
    date: string,
    calculatedData: unknown
  ) => Promise<void>;

  recalculateMonthSummary: (monthId: string) => Promise<void>;

  getClosingBalance: (date: string) => Promise<number>;
  setOpeningBalance: (date: string, openingBalance: number) => Promise<void>;
};
```

The universal system should not know formulas. It only calls adapters.


Do not place a second calendar inside the module.

Do not place another close/reopen bar inside the module.

Module pages can show their own data tables, summaries, and reports, but calendar/day controls must come from the shared system.

## Permission Rules

Owner:

```text
Can close selected day
Can reopen selected day
Can reopen all days
Can close all previous days except today
Can run master calculation refresh
```

Admin:

```text
Can close current day if allowed
Can reopen current day only if allowed
Cannot reopen previous days
Cannot reopen all days
Cannot run master/global refresh unless explicitly allowed
```

Viewer:

```text
Read-only
No close
No reopen
No recalculation
No autosave
```

Disabled buttons should remain visible where useful, but locked with:

```text
Only owner can perform this action.
```
